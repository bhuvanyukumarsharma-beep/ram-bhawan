B. VERSION 1 FACTS AND TRAPS
------------------------------------------------------------------------------
Business rules (do NOT change): bill = fixed rent + water (rate x persons,
default Rs 100 each) + electricity ((new - previous reading) x rate, default Rs
10) - approved deductions. Late interest 24% a year, simple, per day, after the
due date plus grace days. Part payments allowed; money goes to the bill with the
earliest due date first, interest before bill; extra becomes advance credit.
Payment states: pending, approved, rejected, void (screens say "Cancelled").
Roles: owner, admin ("master access"; both = staff), tenant (sees only own
room; reports payments, readings, deduction claims, requests, all needing staff
approval where money is involved). Alerts: Web Push + Gmail through the Edge
Function "notify" (pg_cron). Every number is derived by _ledger(tenancy, as_of)
from bills + approved payments; no stored totals. Two screens must never show
different totals for the same thing.

Technical rules:
 1 Security: every table has row level security ON and no policies; all access is
   through security definer functions taking p_token (_auth/_staff/_owner). The
   lock-down block at the end of supabase/sql/07_notify.sql grants, by NAME, only
   whitelisted functions (list after "if f.proname in ("). tests/grants.test.mjs
   requires the whitelist to equal the functions the website calls (rpc('name')),
   billing_month allowed as legacy. New website-called function: add to BOTH.
   Helpers starting with "_" are never granted.
 2 "create or replace function" cannot change a return type, and a changed
   argument list creates a second overload that stays granted by name. Keep every
   existing name, arguments and return type. Add behaviour through new JSON fields
   or new function names. Test: no name has two overloads.
 3 Parts 02-07 hold only functions + lock-down, so they are re-runnable. Part 01
   (tables) is not. Never put table creation or data inserts in 02-07.
 4 Attachments are base64 data URLs in attachments(data). _save_photo accepts
   data:image/ up to 900,000 characters. get_attachment refuses tenants for files
   they did not upload.
 5 Website: static, hash routing, Netlify. public/config.js holds each owner's
   three public values and is replaced per owner by the helpers. public/sw.js
   does no caching: keep it so.
 6 Tests freeze _today() to 2026-11-04. Free tiers: database 500 MB (photos and
   documents are what can fill it).

Schema changes, idempotent, in supabase/upgrade/01_schema_delta.sql AND in the
same final shape in 01_schema.sql (new columns at the END of each CREATE TABLE):
 - bills.kind text not null default 'regular' check (kind in
   ('regular','previous'))
 - drop constraint bills_tenancy_id_month_key if exists; create partial unique
   index bills_one_regular_per_month on bills (tenancy_id, month) where kind =
   'regular'
 - payments: edited_at timestamptz, edited_by uuid references users(id) on
   delete set null, edit_note text

 - wipe_everything_except_owner also clears them, then writes one line "All test
   data was deleted"; export_all also exports audit_log and the document list
   (no file contents; owner-only as today).

_ledger (supabase/sql/02_engine.sql): the ONLY money-engine edits:
 (a) The value feeding array b_start (today b.month) becomes case when b.kind =
     'previous' then b.due_date else b.month end. Why: old dues use the sentinel
     month 1900-01-01; without this they would exist since 1900, eat payments
     dated before their "owed since" date, show in earlier "as on" views and
     reprinted receipts. With it, such a payment waits as advance credit and is
     used the day the old dues start.
 (b) Each bill and each entry of a payment's 'applied' list carries 'kind'.
 (c) 'awaiting_reading' = b.kind = 'regular' and b.new_reading is null.
 (d) Each adjustment carries 'by' (name of created_by) and 'at' (created_at).
 (e) Each payment carries 'edited_at' and 'edit_note'.
 _tenancy_view with p_staff = false removes 'by': a tenant never learns which
 master did something (test it).

Labels: SQL _bill_label(month, kind) returns 'Old dues' or to_char(month,
'FMMonth YYYY'); use it wherever SQL writes bill text. Website monthLabel and
monthShort return 'Old dues' for the sentinel: nothing may ever print "January
1900".

Update SQL: build.sh makes supabase/setup.sql (parts 01-07; shipped as
database.txt) and supabase/database-update.sql (delta, then parts 02-07; shipped
as database-update.txt). Both end with the same lock-down. The update has no
begin/commit (Supabase runs the text as one unit: any failure changes nothing),
nothing that cannot run in a transaction, a short plain-English header ("run once;
safe to run again"), and ends with: notify pgrst, 'reload schema';
